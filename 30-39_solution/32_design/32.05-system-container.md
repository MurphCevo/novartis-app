# Container Diagram - Project Autopilot (C4 Level 2)

> This document is the narrative companion to the C4 Container diagram. It zooms into the Project Autopilot system boundary and describes the major runtime containers, their responsibilities, the technology choices (known and pending), and how they communicate with each other and with external systems.

## System Boundary

Project Autopilot is a Novartis Australia system. Cevo is the delivery partner engaged to design, build, and hand over the PoC. Everything described below sits within the Autopilot system boundary - deployed into Novartis's AWS environment.

---

## Containers

### 1. Autopilot Assistant (DLV.004)

| Attribute | Detail |
|---|---|
| **Type** | Web application (chat UI) |
| **Technology** | TBD - likely React/Next.js hosted via CloudFront + WAF |
| **Responsibility** | Single natural-language interface for all users. Routes user intent to the appropriate agent(s), manages conversational context, renders results. |
| **Users** | All personas (Marketing Manager, CRM Analyst, MLR Reviewer, Digital Marketing Specialist) |
| **Communicates with** | Agent Orchestrator |

The Assistant is the only container that users interact with directly. It presents a conversational interface and is responsible for:

- Accepting natural language queries and commands
- Displaying agent responses (search results, draft content, tagging proposals)
- Surfacing approval workflows for write-back operations (UC-10)
- Maintaining session and conversation history

---

### 2. Agent Orchestrator

| Attribute | Detail |
|---|---|
| **Type** | Backend service |
| **Technology** | TBD - likely Python/TypeScript, running as a containerised service or Lambda |
| **Responsibility** | Receives requests from the Assistant, determines which agent(s) to invoke, coordinates multi-step workflows, manages agent handoffs. |
| **Communicates with** | Autopilot Assistant, Knowledge Discovery Agent, Content Generation Agent, Asset Tagging Agent, LLM Gateway |

The Orchestrator is the routing and coordination layer. It:

- Interprets user intent (potentially using an LLM classification step)
- Routes to one or more agents
- Manages multi-turn agent interactions
- Handles error states and fallbacks
- Enforces RBAC (which user can invoke which agent/system)

---

### 3. Knowledge Discovery Agent (DLV.001 / UC-4)

| Attribute | Detail |
|---|---|
| **Type** | AI agent |
| **Technology** | Python - RAG pipeline (retrieval-augmented generation) |
| **Responsibility** | Semantic search across approved assets, strategy docs, and campaign performance data. Returns relevant results regardless of query phrasing. |
| **Communicates with** | Agent Orchestrator, Vector Store, Integration Layer, LLM Gateway |

How it works:

1. Receives a natural language query from the Orchestrator
2. Generates embeddings via the LLM Gateway
3. Queries the Vector Store for semantically similar content
4. Optionally queries source systems (via Integration Layer) for real-time data (e.g. campaign metrics)
5. Synthesises results using the LLM and returns a structured response

Data sources accessed (via Integration Layer): all 9 external systems (read-only).

---

### 4. Content Generation Agent (DLV.002 / UC-5)

| Attribute | Detail |
|---|---|
| **Type** | AI agent |
| **Technology** | Python - prompt engineering + template-based generation |
| **Responsibility** | Drafts compliant marketing copy and creative variants from approved templates, content blocks, and audience context. |
| **Communicates with** | Agent Orchestrator, Vector Store, Integration Layer, LLM Gateway |

How it works:

1. Receives a content generation request (campaign brief, audience, therapy area, channel)
2. Retrieves relevant templates and approved content blocks (via Integration Layer)
3. Retrieves compliance rules and claim libraries (via Integration Layer or Vector Store)
4. Generates draft content using the LLM with structured prompts
5. Returns draft for human review - never auto-publishes

Key constraint: all generated content requires human-in-the-loop approval before it leaves the system.

---

### 5. Asset Tagging Agent (DLV.003 / UC-10)

| Attribute | Detail |
|---|---|
| **Type** | AI agent |
| **Technology** | Python - multimodal analysis (text + image) + metadata inference |
| **Responsibility** | Automatically applies consistent metadata to assets (30+ fields) based on content type, therapy area, audience, key message, and usage context. |
| **Communicates with** | Agent Orchestrator, Integration Layer, LLM Gateway |

How it works:

1. Receives an asset (or batch of assets) to tag
2. Analyses content using multimodal LLM (text extraction, image recognition, contextual cues)
3. Proposes metadata tags aligned with Novartis's global metadata taxonomy
4. Presents proposals for human approval
5. On approval, writes tags back to source systems via the Integration Layer

This is the **only agent that writes to external systems**. All write operations require explicit human approval before commit.

---

### 6. Integration Layer (DLV.005)

| Attribute | Detail |
|---|---|
| **Type** | Backend service / adapter layer |
| **Technology** | TBD - API gateway vs MCP servers per system (architecture decision pending) |
| **Responsibility** | Provides a unified interface for agents to read from (and write to) Novartis's 9 external systems. Handles authentication, rate limiting, error handling, and data transformation. |
| **Communicates with** | All 3 agents, all 9 external systems |

The Integration Layer abstracts the complexity of 9 different APIs behind a consistent interface. Each system connection handles:

- Authentication (OAuth2, API keys, tokens - varies per system)
- Request/response transformation
- Rate limiting and retry logic
- Error handling and circuit breaking
- Logging (for auditability)

| External System | Direction | Protocol | Readiness |
|---|---|---|---|
| Veeva Vault PromoMats | Read + Write | API (likely REST) | Low risk |
| Aprimo / Fuse | Read + Write | REST API | Low-Medium |
| SharePoint | Read | Microsoft Graph API | Medium (migration dependency) |
| Sherlock | Read | TBD | High risk (API unknown) |
| Snowflake / CDH | Read | SQL / REST | Low risk |
| Salesforce Marketing Cloud | Read | REST / OAuth2 | Medium (complex auth) |
| Google Analytics 4 | Read | GA4 Data API | Low risk |
| Veeva Oncore CRM | Read | TBD | Medium (API unconfirmed) |
| ShamanGo / Anthill Activator | Read + Write | TBD | High risk (future state) |

### 7. LLM Gateway

| Attribute | Detail |
|---|---|
| **Type** | Infrastructure service |
| **Technology** | AWS Bedrock (potentially via AI Shared Services account or AI Gateway pattern - decision pending) |
| **Responsibility** | Provides LLM inference to all agents. Handles model selection, token management, content filtering, and usage tracking. |
| **Communicates with** | Agent Orchestrator, all 3 agents, AWS Bedrock |

The LLM Gateway is the single point through which all LLM calls flow. This centralisation enables:

- Model governance (only whitelisted models used)
- Token/cost tracking per agent, per user
- Content filtering and guardrails
- Observability and evaluation metrics
- Consistent prompt management

Open questions:
- AI Shared Services account vs project-specific Bedrock deployment
- Whether the AI Gateway pattern (Kade's) is needed as a separate layer
- Cross-region inference and data residency enforcement

---

### 8. Vector Store

| Attribute | Detail |
|---|---|
| **Type** | Data store |
| **Technology** | TBD - likely Amazon OpenSearch Serverless or pgvector |
| **Responsibility** | Stores embeddings of indexed content (assets, documents, templates) for semantic search. |
| **Communicates with** | Knowledge Discovery Agent, Content Generation Agent |

The Vector Store is populated by an indexing pipeline (not yet detailed) that:

- Reads content from source systems via the Integration Layer
- Generates embeddings via the LLM Gateway
- Stores embeddings with metadata for retrieval

This is the foundation of the RAG (retrieval-augmented generation) pattern used by UC-4 and UC-5.

---

### 9. Observability and Audit

| Attribute | Detail |
|---|---|
| **Type** | Cross-cutting infrastructure |
| **Technology** | TBD - CloudWatch, custom dashboards, audit log store |
| **Responsibility** | LLM evaluation metrics, query/result logging, audit trail for compliance, RBAC enforcement logging. |
| **Communicates with** | All containers (receives logs/events) |

Every interaction - user queries, agent responses, LLM calls, integration requests, and write-back approvals - is logged. This supports:

- Compliance auditability (who asked what, what was generated, what was approved)
- LLM quality evaluation (accuracy, relevance, hallucination detection)
- Performance monitoring (latency, error rates)
- Cost tracking (LLM token usage per agent/user)

## Key Architecture Decisions (Settled)

| Decision | Rationale |
|---|---|
| Single chat interface (not one UI per agent) | Reduces cognitive load for users; orchestrator handles routing |
| Human-in-the-loop for all write operations | Non-negotiable in regulated pharma context (GP-1) |
| Centralised LLM Gateway | Enables model governance, cost control, and observability |
| Integration Layer as abstraction | Agents don't need to know API specifics; adapters can change without agent changes |
| No base model training on Novartis data | Governance prohibition. RAG + fine-tuning on approved copy are the permitted approaches. |
